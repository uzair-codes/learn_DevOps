# Kubernetes Ingress Controller Deep Dive

In the previous section, we learned:

* what Ingress is
* why Kubernetes Services alone are not enough
* how Ingress solves routing and cost problems

Now we will go deeper and understand the most important component behind Ingress:

# Ingress Controller

This is the actual engine that makes Ingress work.

Without an Ingress Controller:

* Ingress YAML files are useless
* routing rules do nothing
* Kubernetes cannot process Ingress traffic

---

# Important Concept

Kubernetes does NOT provide an Ingress Controller by default.

Kubernetes only provides:

* the Ingress API object
* the Ingress resource definition

But Kubernetes itself does not know:

* how to route traffic
* how to process HTTP requests
* how to handle load balancing

That responsibility belongs to:

# Ingress Controllers

---

# What is an Ingress Controller?

An Ingress Controller is a software component that:

* watches Ingress resources
* reads routing rules
* receives external traffic
* forwards traffic to correct Services

You can think of it as:

* reverse proxy
* smart load balancer
* traffic manager
* HTTP router

---

# Simple Real-Life Example

Imagine a large shopping mall.

At the main entrance:

* a receptionist receives visitors
* checks where they want to go
* guides them to the correct shop

Ingress Controller works exactly like that receptionist.

It:

* receives incoming requests
* checks rules
* sends traffic to the correct backend Service

---

# Important Architecture Concept

Ingress Controllers can run in two ways:

1. Inside the Kubernetes Cluster
2. Outside the Kubernetes Cluster

This is extremely important to understand.

---

# 1. Ingress Controller Running INSIDE the Cluster

This is the most common approach.

Example:

* NGINX Ingress Controller

---

# How It Works

The Ingress Controller runs:

* as Pods
* inside Kubernetes

This means:

* controller itself is part of the cluster

Usually:

* Deployment
* Pods
* Service

are created for the controller.

---

# Traffic Flow

```text id="jlwm1e"
Internet

   ↓
Ingress Controller Pod
   ↓
Kubernetes Services
   ↓
Application Pods
```

---

# 2. Ingress Controller Running OUTSIDE the Cluster

Now comes the more advanced enterprise model.

In some enterprise environments:

* load balancer does not run inside Kubernetes

Instead:

* external hardware
* cloud-native load balancer
* enterprise appliance

handles traffic.

---

# Examples

Examples include:

* F5 Networks BIG-IP
* Amazon Web Services ALB
* hardware load balancers
* enterprise network appliances

---

# Important Question

If the load balancer is outside Kubernetes:

> How does it know where Pods are running?

Because Pods:

* constantly change
* get new IPs
* move between nodes

This creates a networking challenge.

---

# How External Controllers Communicate with Kubernetes

There are two common methods:

1. NodePort Method
2. Direct Routing / VXLAN / VPC Networking

---

# Method 1 — NodePort-Based Communication

This is the traditional and simpler method.

---

# How NodePort Works

When a Service uses:

```yaml id="pb0m1w"
type: NodePort
```

Kubernetes opens a port on every worker node.

Example:

```text id="u0n2u0"
Node IP: 192.168.1.10
Port: 31234
```

External load balancer forwards traffic to:

* worker node IP
* NodePort

Then Kubernetes internally forwards traffic to Pods.

---

# Full Traffic Flow

```text id="45pv6q"
Internet
   ↓
External Load Balancer
   ↓
Worker Node IP + NodePort
   ↓
Kubernetes Service
   ↓
Pod
```

---

# Advantages

* simple
* widely supported
* easy integration

---

# Disadvantages

* extra network hop
* less efficient
* more latency

---

# Method 2 — Direct Routing / VPC Networking / VXLAN

This is more advanced and more efficient.

Used heavily in:

* enterprise networking
* cloud-native systems

---

# Direct Pod Routing

In some cloud platforms like:

* Amazon Elastic Kubernetes Service

Pods receive:

* real VPC IP addresses

This means:

* external load balancer can directly communicate with Pods

without using NodePort.

---

# Benefits

* lower latency
* better performance
* fewer network layers
* direct communication

---

# VXLAN Tunneling

Enterprise systems like:

* F5 BIG-IP

may create secure network tunnels into Kubernetes.

These tunnels allow:

* direct communication with Pod networks

even though the load balancer exists outside the cluster.

---

# Simplified Analogy

Imagine:

* Kubernetes cluster = private office building
* external load balancer = delivery company

NodePort method:

* delivery reaches building reception first

Direct routing:

* delivery goes directly to office room

Direct routing is faster and smarter.

# Important Ingress Concepts

Now let us understand three extremely important routing concepts.

---

# 1. Path-Based Routing

Traffic routed using URL paths.

Example:

```text id="6m9hmq"
/login
/payment
/search
```

Routing example:

| Path     | Destination     |
| -------- | --------------- |
| /login   | login-service   |
| /payment | payment-service |
| /search  | search-service  |

---

# Why Useful?

Allows multiple applications behind:

* single domain
* single public IP

---

# Example

```text id="eqo78f"
my-website.com/login
my-website.com/payment
```

---

# 2. Host-Based Routing

Traffic routed using domain names.

Example:

| Hostname          | Destination   |
| ----------------- | ------------- |
| api.example.com   | API Service   |
| shop.example.com  | Shop Service  |
| admin.example.com | Admin Service |

---

# Why Useful?

Allows:

* multiple websites
* same Kubernetes cluster
* same public IP

---

# Example

```text id="kxg9dj"
shop.example.com
api.example.com
admin.example.com
```

---

# 3. Ingress Class

Ingress Class specifies:

> Which Ingress Controller should process this Ingress resource.

---

# Why Needed?

Sometimes clusters contain:

* multiple controllers

Example:

* NGINX controller
* HAProxy controller

Ingress Class prevents conflicts.

---

# Example

```yaml id="ys31d6"
ingressClassName: nginx
```

This means:

* only NGINX controller should process this Ingress

---

# Important Production Reality

In enterprise environments:

* multiple teams
* multiple applications
* multiple controllers

may exist together.

Ingress Class becomes extremely important for proper traffic separation.
