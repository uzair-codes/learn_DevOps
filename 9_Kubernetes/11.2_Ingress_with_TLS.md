# TLS / HTTPS with Ingress

This topic is extremely important because modern applications must be secure.

Almost every professional website today uses:

```text id="9ft9fe"
https://
```

instead of:

```text id="x3t7cq"
http://
```

---

# What is HTTPS?

HTTPS means:

# HyperText Transfer Protocol Secure

It encrypts communication between:

* user browser
* server

This prevents attackers from reading sensitive data like:

* passwords
* banking information
* API tokens
* personal information

---

# Real-Life Example

Imagine sending a letter.

---

## HTTP (Not Secure)

You send the letter openly.

Anyone in the middle can:

* read it
* modify it
* steal information

---

## HTTPS (Secure)

You place the letter inside:

* locked envelope
* sealed package

Only intended receiver can open it.

This is exactly what HTTPS does using:

* encryption
* SSL/TLS certificates

---

# What is TLS?

TLS means:

# Transport Layer Security

Older term:

* SSL (Secure Sockets Layer)

Modern systems use:

* TLS

but people still commonly say:

* SSL certificate

Both terms are often used interchangeably.

---

# What Happens Without TLS?

Without TLS:

* traffic is plain text
* passwords can be intercepted
* APIs become insecure
* attackers can sniff network traffic

This is dangerous in:

* public WiFi
* cloud environments
* enterprise networks

---

# Role of Ingress in TLS

Ingress makes HTTPS management much easier.

Instead of configuring certificates:

* separately on every Pod
* separately on every application

Ingress centralizes everything.

---

# Major Advantage

With Ingress:

* one central place handles HTTPS
* certificates managed centrally
* backend applications remain simpler

This is one of the biggest reasons production systems use Ingress.

---

# How TLS Works in Kubernetes Ingress

There are two major steps:

1. Store certificate in Kubernetes Secret
2. Reference that Secret inside Ingress YAML

---

# Step 1 — Create TLS Secret

Suppose you have:

* certificate file
* private key file

Example:

```text id="wx6l0l"
tls.crt
tls.key
```

Now create Kubernetes Secret.

---

# Command

```bash id="9m9m3s"
kubectl create secret tls my-tls-secret \
  --cert=tls.crt \
  --key=tls.key
```

---

# What This Does

Kubernetes creates a Secret named:

```text id="kc2v4i"
my-tls-secret
```

This Secret securely stores:

* SSL certificate
* private key

---

# Why Use Kubernetes Secret?

Because certificates are sensitive data.

Private keys must not be exposed publicly.

Secrets help securely store:

* passwords
* API keys
* certificates

inside Kubernetes.

---

# Step 2 — Use Secret in Ingress

Now reference Secret inside Ingress YAML.

---

# Example Ingress with TLS

```yaml id="jlwm9p"
apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: secure-ingress

spec:
  ingressClassName: nginx

  tls:
  - hosts:
    - my-website.com
    secretName: my-tls-secret

  rules:
  - host: my-website.com

    http:
      paths:
      - path: /
        pathType: Prefix

        backend:
          service:
            name: login-service
            port:
              number: 80
```

---

# Understanding This YAML

---

## TLS Section

```yaml id="8j7v9t"
tls:
```

This enables HTTPS support.

---

## Hosts

```yaml id="yykr4g"
hosts:
- my-website.com
```

Specifies which domain uses TLS.

---

## Secret Name

```yaml id="f3m2l5"
secretName: my-tls-secret
```

Ingress Controller loads:

* certificate
* private key

from this Secret.

---

# What Happens Internally?

When user opens:

```text id="z9a5w4"
https://my-website.com
```

the flow becomes:

```text id="2uk7cc"
Browser
   ↓
Ingress Controller
   ↓
TLS Certificate Validation
   ↓
Secure Encrypted Connection
   ↓
Backend Service
   ↓
Pod
```

---

# Role of Ingress Controller in TLS

Ingress Controller:

* receives encrypted traffic
* handles certificates
* decrypts HTTPS requests
* forwards traffic internally

This is called:

# TLS Termination

We will study this deeply now.

---

# Three TLS Techniques in Ingress

Production environments commonly use three approaches:

1. SSL Offloading (TLS Termination)
2. SSL Passthrough
3. SSL Bridging (Re-encryption)

These are extremely important interview and real-world concepts.

---

# 1. SSL Offloading (TLS Termination)

This is the most common method.

---

# How It Works

Client sends:

```text id="y6e2p3"
HTTPS Request
```

Ingress Controller:

* decrypts traffic
* processes request
* sends plain HTTP internally

---

# Flow

```text id="84n7jv"
User Browser
   ↓ HTTPS
Ingress Controller
   ↓ HTTP
Backend Pod
```

---

# Why Called Offloading?

Because backend applications do not handle encryption.

Ingress Controller handles all TLS work.

It "offloads" encryption burden from applications.

---

# Advantages

* faster backend applications
* centralized certificate management
* simpler applications
* lower CPU usage on Pods

---

# Disadvantage

Traffic inside cluster becomes:

* plain HTTP

Internal traffic is not encrypted.

---

# 2. SSL Passthrough

This is more secure internally.

---

# How It Works

Ingress Controller does NOT decrypt traffic.

Instead:

* encrypted traffic directly forwarded to Pods

Pods themselves handle TLS.

---

# Flow

```text id="bj9y90"
User Browser
   ↓ HTTPS
Ingress Controller
   ↓ HTTPS
Backend Pod
```

---

# Advantages

* end-to-end encryption
* internal traffic remains secure

---

# Major Limitation

Ingress Controller cannot inspect HTTP contents.

That means:

* no advanced Layer 7 routing
* limited path-based routing
* reduced traffic intelligence

Because encrypted traffic cannot be read.

---

# 3. SSL Bridging (TLS Re-Encryption)

This is the most secure and enterprise-grade approach.

---

# How It Works

Ingress Controller:

1. decrypts incoming traffic
2. inspects request
3. optionally checks security rules
4. re-encrypts traffic
5. forwards encrypted traffic to backend

---

# Flow

```text id="llsyqs"
User Browser
   ↓ HTTPS
Ingress Controller
   ↓ HTTPS
Backend Pod
```

But unlike Passthrough:

* controller actually reads traffic first

then encrypts again.

---

# Advantages

* Layer 7 routing available
* encrypted internal traffic
* advanced security inspection
* enterprise-level protection

---

# Disadvantages

* more CPU usage
* more complexity
* slightly higher latency

---

# Comparison of TLS Methods

| Method | Traffic to Backend | Can Read HTTP Data? | Security Level |
|---|---|---|
| SSL Offloading | HTTP | Yes | Medium |
| SSL Passthrough | HTTPS | No | High |
| SSL Bridging | HTTPS | Yes | Very High |

---

# Which Method is Most Common?

Most Kubernetes environments use:

# SSL Offloading

because:

* simpler
* faster
* easier management

Large enterprises with strict compliance may use:

* SSL Bridging

---

# Self-Signed Certificates

During local development:

* developers often create self-signed certificates

These are certificates created manually instead of being issued by trusted Certificate Authorities.

---

# Important Note

Browsers usually show warnings like:

```text id="h2zcl6"
Your connection is not private
```

because self-signed certificates are not trusted globally.

This is normal in local labs and testing environments.

---

# Example — Create Self-Signed Certificate Using OpenSSL

Using OpenSSL:

```bash id="28cz6t"
openssl req -x509 -nodes -days 365 \
-newkey rsa:2048 \
-keyout tls.key \
-out tls.crt
```

This generates:

* tls.crt
* tls.key

---

# Testing HTTPS with Curl

Example:

```bash id="z0k8k4"
curl -v -k https://my-website.com
```

---

# Meaning of `-k`

```text id="2b4q9u"
-k
```

means:

* ignore certificate validation

Useful for:

* self-signed certificates
* local testing

---

# Advanced Local Domain Testing

Sometimes developers use:

```bash id="5q4jyc"
curl --resolve
```

Example:

```bash id="k8jlwm"
curl -v -k \
--resolve my-website.com:443:192.168.49.2 \
https://my-website.com
```

This manually maps:

* domain
* IP address

without modifying DNS.

---

# Production TLS Best Practices

In real production environments:

* never use self-signed certificates
* use trusted Certificate Authorities
* automate certificate renewal
* protect private keys
* rotate certificates regularly

Popular production tools:

* Let’s Encrypt
* Cert-Manager

---

# Important Production Concept — Cert-Manager

cert-manager is widely used in Kubernetes.

It automatically:

* requests certificates
* renews certificates
* manages TLS Secrets

This removes manual SSL management.
